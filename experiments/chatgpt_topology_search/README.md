# ChatGPT主導トポロジー探索 — 専用作業フォルダ

**全体方針と保存先の早見表**は[Phase 2研究・フォルダ運用ガイド](../../docs/research_workflow_ja.md)を参照してください。

**本ディレクトリが、今後のChatGPT主導によるRF LPF回路の考案・専用最適化・比較実験の標準作業場所です。**

GitHub上のパス: `experiments/chatgpt_topology_search/`

- 日付・実験IDごとの作業場所: `runs/EXP-NNN/` （例: `runs/EXP-001/`）
- 新しい実験は、`templates/`の雛形をコピーして作成する。
- 過去のChatGPT発案回路LPF-005/006は `../no_pcb_policy_update_20261011/`、LPF-007/008は `../no_pcb_tunable_shunt_20261011/` に残す。履歴ファイルを勝手に移動しない。
- GitHub上のフォルダは**永続的な研究成果物の保存先**であり、ChatGPTの一時Python環境のローカルパスと同一ではない。作業開始時にリポジトリのブランチ・コミットを確認し、終了時に必要な結果をGitHubへコミット/PRする。

## 何を置くか

| 場所 | 内容 | 例 |
|---|---|---|
| `runs/EXP-NNN/config.json` | 探索仮説、対象モデル・周波数・固定制約、変数境界、seed、計算予算 | 仕様バージョン、`objective=full_lpf` |
| `runs/EXP-NNN/circuit.json` | **実験内の暫定回路**。枝接続、L/C/Q、可変Cの対GND接続点、チップ物理列、結合、6設定のC | 汎用回路モデルで再現できる記述 |
| `runs/EXP-NNN/optimize.py` | 当該構造に専用の高速解析・最適化コード（必要な場合） | 縮約回路、構造固有の初期値生成 |
| `runs/EXP-NNN/results.json` | **実際に得た**探索数値・収束、評価回数、周波数グリッド、検証状態 | 未実行なら作らない、値を捏造しない |
| `runs/EXP-NNN/summary.md` | 仮説と回路図、結果、未解決事項、基準候補との比較、次の改良方針 | LPF-007との35dB同条件比較 |
| `runs/EXP-NNN/artifacts/` | 軽量なグラフ・ログ・画像・要約など | 大容量チェックポイントはActions Artifacts参照 |

`runs/EXP-NNN`は**新規実験**の作業単位であり、正式な候補ID `LPF-xxx`とは異なる。`EXP-NNN`はこのディレクトリ内で重複させず、実験開始時に採番する。自動生成探索はここに置かず、当面は`../matching_limit/`の既存処理を使用する。

## 他フォルダとの境界

- **共有回路解析・検証**: `../../src/lpf/` のMNA、独立解析、6設定評価と制約チェックを使用。専用解析器だけの結果を最終検証としない。
- **共有ソルバに昇格**: 複数のトポロジーに使える処理は回帰テストとともに`../../src/lpf/`へ移す。古い実験の再現入口は壊さない。
- **全プロジェクト共通のCLI**: `../../scripts/`。個別実験の局所CLIは実験内に置いてよい。
- **公認の比較対象・有望候補**: 独立検証後、`../../candidates/LPF-xxx.json`および`../../data/candidate_index.csv`へ明示的に昇格。暫定解を自動登録しない。
- **承認済み設計制約**: `../../data/design_constraints.json`、帯域は`../../data/bands.csv`。実験都合で制約を上書きしない。
- **体系的トポロジー探索**: `../matching_limit/`。良好解の初期値移植と独立比較を行うが、現在は可変Cの内部ノード配置一般化が**未実装**。

## 標準ワークフロー

1. **仮説**: 回路理論に基づく構造と損失低減メカニズムを`summary.md`に記し、`config.json`で`matching_only`か`full_lpf`かを宣言する。
2. **回路モデル**: GND・入出力・内部ノード、固定枝、2枝以内の可変対GND IC C、磁気結合の物理列、6設定共通の固定素子を明記する。内部ノードへの可変Cは許容される。
3. **予備最適化**: 構造固有の専用縮約モデルを使う場合は数学的適用条件を記録。最適化の収束失敗と計算ジョブ失敗を区別する。
4. **共通の独立検証**: `lpf.circuit.solve`、`lpf.independent.solve_gain`等によってUL/DL最大IL、UL H2/H3最小減衰、電力収支、結合行列SPD、コスト・接続制約をチェックする。全帯域有限メッシュは連続周波数の数学的保証ではない。
5. **比較**: `../../candidates/LPF-007.json`と**同一RF条件・同一周波数グリッド**で評価。35dB公称条件達成と30dB必須条件達成を別々に示す。
6. **結果の確定**: 実行したコードSHA、依存バージョン、seed、設定、評価回数、時間、最大IL/H2/H3、収束、未確認物理項目を`results.json`と`summary.md`へ記録。良好候補は正式登録のためPRを作成する。

大規模・長時間の最適化は原則GitHub Actionsの手動起動で行い、実行run IDとArtifact保存情報を記録する。Actions自体の実装は `../../.github/workflows/` に置く。

## 今の第一目標

現行制約に適合するfull-LPFの先行候補**LPF-007**（6設定最大IL 0.513168414dB、H2/H3約35.07dB、有限グリッド・最適化未収束）に対して、**H2/H3をともに35dB以上維持し、最大ILを下げる**回路を見つけること。公称の最終数値目標は最大IL≤0.30dB。従来のLPF-007を超えたという主張には、独立検証と比較条件の記録が必要。
